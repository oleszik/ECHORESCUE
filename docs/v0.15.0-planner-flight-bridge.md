# v0.15.0 planner-flight bridge

## Scope and trust boundary

v0.15.0 connects the existing deterministic cardinal A* implementation to the
v0.14.4 waypoint executor in the static v0.14.5 indoor world. It is known-map,
single-level, fixed-altitude, simulation-only navigation. It does not add
discovery, SLAM, sensor-derived occupancy, obstacle perception, dynamic
replanning, generalized 3D planning, survivor work or multi-drone flight.

```text
versioned known map -> existing planning.astar -> checked ENU adapter
                                                   |
                                                   v
configured relative targets -> v0.14.4 executor <- MAVLink telemetry

Gazebo pose/contact -> independent evaluator -> acceptance report only
```

Planning completes before the flight harness starts. Rejection therefore
creates no mission process and sends no command. During flight the controller
uses only generated targets and telemetry. See [ADR 0021](adr/0021-known-map-grid-to-enu-planning-boundary.md).

## Map and transform

[`config/planner-flight-v0.15.0.json`](../config/planner-flight-v0.15.0.json)
contains a 25-column by 17-row map at 0.5 m/cell. Occupancy rows are stored
south-to-north. Columns increase east; rows increase north. For row `r` and
column `c`, relative cell-centre ENU is:

```text
east  = -2.25 + (c + 0.5) * 0.5
north = -4.25 + (r + 0.5) * 0.5
```

Thus configured launch cell `(8,4)` maps exactly to relative `(0,0)`. At
runtime that offset is added to the observed launch-local ENU anchor. The
second-room goal `(12,20)` maps to `(8,2)`.

The known occupied cells represent the outer shell, divider and blocker.
Inflation uses the 0.35 m vehicle radius plus 0.20 m margin and the cell
half-diagonal. The valid doorway remains connected; a deliberately narrowed
doorway does not. Only cardinal connectivity is accepted. Compaction removes
collinear cells without diagonal shortcuts and revalidates every segment.

## Deterministic route

Existing A* produces cost 20 in each direction. Raw paths and executable
targets are stored separately in the reports. The compacted paths are:

```text
outbound: (8,4) -> (9,4) -> (9,14) -> (12,14) -> (12,20)
return:   (12,20) -> (12,14) -> (9,14) -> (9,4) -> (8,4)
```

Their nine target IDs are generated as `launch-stabilize`, three outbound
turns, `outbound-goal`, three return turns and `return-launch`. They are not a
manually authored waypoint list.

## Commands

Use the documented Jazzy simulator environment and source the built workspace.
The prerequisite venv must be created with `--system-site-packages` so the
apt-installed `rclpy` can import its PyYAML and NumPy dependencies.

```bash
./scripts/run_planner_flight_integration.sh diagnose

./scripts/run_planner_flight_integration.sh \
  --output artifacts/v0.15.0-planner-flight-graphical.json \
  smoke --graphical --timeout 260

./scripts/run_planner_flight_integration.sh \
  --output artifacts/v0.15.0-planner-flight-headless.json \
  smoke --timeout 260

./scripts/run_planner_flight_integration.sh \
  --output artifacts/v0.15.0-blocked-goal.json negative-blocked-goal

./scripts/run_planner_flight_integration.sh \
  --output artifacts/v0.15.0-unsafe-clearance.json negative-clearance
```

## Acceptance evidence

The real owned-stack graphical and headless runs both passed. Each run planned
cost-20 outbound and return paths, executed and independently observed all nine
generated targets in order, crossed the doorway twice, entered the planned
goal region, returned, landed and disarmed. The graphical run's minimum goal
error was 0.061 m, obstacle surface clearance was 0.306 m and doorway surface
clearance was 0.355 m. The headless values were 0.060 m, 0.307 m and 0.355 m.
All owned processes stopped, the mission and observer disappeared from the ROS
graph, and UDP 9002/14550 plus TCP 5760 were free after both runs.

The blocked-goal and unsafe-clearance reports both passed by rejecting the
plan before any process or command was started. A fresh v0.14.5 collision
negative also passed: both the conservative envelope and Gazebo contact sensor
detected the deliberately injected obstacle collision, followed by clean
teardown.

The checked-in evidence is:

- [`artifacts/v0.15.0-planner-flight-graphical.json`](../artifacts/v0.15.0-planner-flight-graphical.json)
- [`artifacts/v0.15.0-planner-flight-headless.json`](../artifacts/v0.15.0-planner-flight-headless.json)
- [`artifacts/v0.15.0-blocked-goal.json`](../artifacts/v0.15.0-blocked-goal.json)
- [`artifacts/v0.15.0-unsafe-clearance.json`](../artifacts/v0.15.0-unsafe-clearance.json)

Each planning section contains the map and transform versions, raw and
compacted paths, costs and generated targets. Execution remains a separate
section containing telemetry mission, ROS observer, Gazebo evaluation,
process-exit and cleanup evidence.

## Limitations

- The known map is repository-authored and static; it is not updated from
  simulated or onboard sensors.
- Inflation and the configured map are conservative discrete approximations.
  Gazebo evaluation is independent evidence, not a planning input.
- Return is planned before takeoff from the declared outbound goal to launch.
  Any airborne failure lands through existing bounded recovery; it never
  replans.
- One fixed cruise altitude turns this into 2D planning plus flight adaptation,
  not generalized 3D planning.
- Results apply only to the pinned simulator and are not real-aircraft safety
  evidence.
