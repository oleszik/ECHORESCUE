# v0.9 — Generalized Roles and Failure Resilience

## Motivation and architecture audit

v0.9 asks how an N-agent search-and-rescue fleet can retain explicit task
ownership and recover deterministically when an agent fails during useful work.
The implementation extends the current N-agent/v0.8 core; it does not replace
the established frontier allocator, A* planner, deconfliction shield, energy
model, communication graph, dynamic-obstacle model, or Survivor evidence
tracking.

The audit found that the main simulation already stores runtimes and failure
schedules as collections, accepts any configured agent ID, supports sequential
failures on different agents, treats failed positions as static blockers, and
defines mission success over the remaining operational agents. Frontier
allocation and conflict resolution are N-agent algorithms. The old failure
reassignment was also collection-based, but its tasks were implicit
`Position -> owner` entries: they had no stable identity, type, lifecycle,
explicit role, recovery latency, or energy/load-aware candidate score.

The remaining historical two-agent assumptions are confined to Adaptive and
Network-aware Relay: their configuration requires exactly two agents and their
link/partner logic names `drone-1`, `drone-2`, or a single other drone. v0.9
represents `RELAY` as role data and records actual Relay transitions, but it
does not generalize that planner into Multi-Relay. That boundary belongs to
v0.10.

## Role and task model

Roles are data in `AgentRole`: `GENERALIST`, `SCOUT`, `VERIFIER`, and `RELAY`.
They influence reassignment preference; they do not select a separate planner.
The `off` policy preserves legacy behavior and replay bytes. `generalist`
enables explicit tasks with all agents as Generalists. `generalized` assigns
roles by sorted agent ID: half the fleet are Scouts, one quarter (minimum one)
are Verifiers, and the remainder are Generalists. One agent always degrades to
Generalist. Thus 1/2/4/8 agents initialize as G, S+V, S+S+V+G, and
S+S+S+S+V+V+G+G. `RELAY` is assigned only by an explicitly enabled existing
Relay strategy.

`MissionTask` covers `exploration`, `survivor_verification`,
`relay_positioning`, and `return_home`. Every task has a deterministic ID,
type, one owner or no owner, status, target, creation step, priority, original
owner, and lifecycle timestamps. `TaskRegistry` enforces at most one active
task per owner. Failure removes the owner exactly once and changes the task to
`orphaned`; reassignment updates that same task object and ID rather than
creating duplicate work.

## Failure recovery and deterministic scoring

On a scheduled failure the current task is orphaned before the runtime becomes
`FAILED`. The agent stops, emits no normal traffic, receives no task, remains a
static obstacle, and is excluded from the operational-return denominator.
Each operational, exploring, non-holding agent is evaluated on current known
traversability. A candidate must have both a known-safe path to the task and a
known return path, and its remaining battery must cover both paths plus the
existing RTB safety reserve.

The frozen score is:

```text
path edges
+ 5 if the original target must be replaced by another frontier
+ 4 * active task count
+ role penalty (preferred 0, Generalist 3, other specialist 6)
+ floor(consumed energy / 20)
```

Candidates first compete for the exact orphaned target. Only if no eligible
agent can reach it does the allocator consider another valid frontier. The
stable tie-break is score, path cost, remaining energy descending, agent ID,
then target position. The winner alone receives the task; all losers retain
their current work. The existing allocator and motion deconfliction remain the
single execution path.

When a winner's role does not match the task preference under `generalized`, it
temporarily adopts the preferred role with reason `failure_recovery`. That
role is sticky until the recovered task completes, then the agent returns to
its base role. Existing Relay entry/exit also produces explicit role events.
Every change records agent, old/new role, reason, step, and task where
applicable. More than two changes for one agent is flagged as thrashing; no
holdout run crossed that boundary.

Assignment latency is `reassigned step - orphaned step`. Execution recovery
latency is `first successful movement on the reassigned task - orphaned step`.
The latter deliberately measures resumed productive execution, not merely a
registry update.

## Telemetry, replay, and dashboard

Role-enabled missions use replay schema 2.3. Frames contain each agent's role
and active task ID plus a global task-ownership snapshot. Events cover initial
role assignment, failure, orphaning, reassignment and score, role transition,
productive recovery, and completion by the new owner. Metrics include failure,
task, assignment/recovery latency, role-change/takeover, Recall, mission, and
operational-return results. Role policy `off` omits the new fields and retains
legacy replay behavior; the dashboard continues to accept schema 2.2.

The dashboard adds one Role badge and owned-task field per N-agent card, keeps
the existing `FAILED` state, and adds distinct event styling and details for
orphaning, reassignment, recovery, and role changes. It remains a read-only
viewer rather than a team-management system.

## Development set and frozen policy

Seeds 0–9 were used to compare fixed failure steps 4, 8, 12, 16, and 20. Every
candidate recovered all ten missions. `drone-2:12` was frozen because every
failure occurred during active task ownership, after meaningful parallel work,
and execution recovery was observable (normally one step, once two steps).
With the selected step the development means were 68.7 steps for Generalist
failure and 66.8 for Generalized-role failure. The score constants above and
sticky transition rule were frozen before viewing seeds 50–99. No holdout
result was used to tune them.

Paired B−A failure overhead was +6.68±23.12 steps, median +4
`[-10,+165]`, and −22.72±45.07 path cells, median −31 `[-65,+277]`.
Paired D−C overhead was +6.38±23.13 steps, median +4 `[-10,+165]`, and
−22.44±44.75 path cells, median −30 `[-59,+277]`. The negative mean path
delta is not an efficiency claim: the failed agent stops accumulating path,
while configured-fleet path totals include its pre-failure movement.

Under failure, D−B is −0.30±2.49 steps, median 0 `[-10,+10]`, and
+0.28±4.53 path cells, median 0 `[-18,+16]`. Roles therefore provide explicit,
auditable specialization and 12 emergency takeovers, but no broad performance
advantage on this isolated holdout. That mixed result is retained without
post-holdout tuning.

## Failure analysis and safety

- Largest Generalized failure-duration overheads: seed 77 (+165), 59/86
  (+14), 84 (+12), and 83 (+10). Largest path overheads: 77 (+277), 90
  (+13), 59 (+3), 61/84 (−7).
- Roles were faster than Generalist-only on seeds 51, 53, 58, 64, 78, 90,
  and 97; slower on 52, 63, 75, and 86; all other duration deltas were zero.
- Seeds 52, 63, 64, 68, 69, 72, 75, 76, and 85 had unusually little failure
  effect under the benchmark's explicit threshold.
- There were no slow-recovery, reassignment-failure, thrashing, Recall-loss,
  or mission-failure seeds. Every assignment occurred in the failure step and
  productive movement resumed one step later.
- All 200 scenario missions had zero wall and drone collisions. Failed agents
  remained stationary obstacles and all 700 operational-agent return
  opportunities succeeded.

The targeted Failure + Moderate Dynamic Obstacles regression verifies that the
failed body and persistent closure are both respected, reassignment/replanning
complete, and collisions remain zero. The Failure + Moderate Noise regression
is repeat-deterministic and keeps hypothesis/evidence metrics consistent. A
sequential two-failure test demonstrates architecture support without claiming
a full probabilistic multi-failure study. The seed-96 regression preserves a
critical edge case: an isolated frontier behind a failed body cannot keep the
otherwise completed fleet alive until `max_steps`.

## Demo

[`seed_50_generalized_roles_failure.json`](../replays/seed_50_generalized_roles_failure.json)
is the single v0.9 replay. Four agents begin as two Scouts, one Verifier, and
one Generalist. At step 12 `drone-2` fails during exploration and
`task-000031` becomes orphaned. Multiple operational candidates are evaluated;
`drone-4` wins with score 13, becomes a temporary Scout, and owns that same
task ID. Productive execution resumes at step 13, the task completes at step
17, and `drone-4` returns to Generalist. All three Survivors are confirmed,
all three operational agents land, the failed agent stays at `(6,7)`, and the
65-step mission has zero collisions.

```bash
python -m echorescue --seed 50 --drones 4 --role-policy generalized \
  --inject-failure drone-2:12 \
  --replay-out replays/seed_50_generalized_roles_failure.json
python -m echorescue.dashboard \
  --replay replays/seed_50_generalized_roles_failure.json \
  --benchmark benchmarks/generalized_roles_failure_50_holdout_seeds.json
```

## Limitations and next research question

Role/task truth is centrally consistent in shared mode. Constrained/local mode
retains its existing transport and is covered only regressively; v0.9 adds no
distributed consensus. The generic `RELAY` state wraps the existing two-agent
Relay mechanism, which remains intentionally limited to exactly two agents.
There is no Multi-Relay placement, graph-wide relay optimization, predictive
communication, probabilistic failure distribution, diagnosis, repair, task
preemption market, new sensor fusion, or new planner. Role preferences affect
failure reassignment, not routine frontier allocation, so no-failure
Generalist and Generalized runs are intentionally identical here.

v0.9 is complete under its acceptance criteria. The next separate research
question is v0.10 Predictive Communication / Multi-Relay; it is not implemented
in this slice.
