# v0.15.1 sensor-driven obstacle discovery and bounded replanning

## Scope and architecture

v0.15.1 adds one real Gazebo horizontal lidar to the existing Iris simulation.
An obstacle omitted from the repository prior map is sensed after takeoff,
projected into the EchoRescue occupancy grid, conservatively inflated and used
to invalidate the remaining route. The replacement route calls the existing
`echorescue.planning.astar` implementation directly. This milestone remains
simulation-only, single-drone and fixed-altitude.

```text
Gazebo lidar -> sensor-only adapter -> typed RangeObstacleObservation
                                             + fresh same-session telemetry pose
                                             v
prior map -> deterministic occupied update -> conservative inflation
                                             v
remaining-route intersection -> bounded A* -> waypoint executor -> MAVLink

Gazebo pose/contact -----------------------> independent evaluator only
ROS state/events --------------------------> independent observer only
```

[ADR 0022](adr/0022-sensor-map-planner-trust-boundary.md) defines the trust
boundary. Production mapping and control do not read Gazebo pose, contacts,
collision geometry or evaluator results.

## Sensor and mapping contract

`RangeObstacleObservation.msg` contains ROS header/frame, telemetry session,
strict sequence, simulator sensor time, monotonic receipt time, angle origin and
increment, declared range limits and samples. The configured scan is horizontal
360 degrees, 72 beams, 10 Hz, 0.25–4.0 m, mounted in
`iris_range_link`. Gazebo `+inf` no-return values become exactly 4.0 m at the
typed boundary and do not mark a cell.

Mapping requires a finite telemetry position and heading from the same session.
Observation age, pose age and their receipt skew are each bounded. Empty,
stale, cross-session, duplicate/out-of-order, non-finite, below-minimum and
above-maximum scans are rejected without mutation. Accepted hit endpoints are
rotated by telemetry ENU heading, translated relative to the recorded launch,
mapped deterministically to a cell and inflated by the existing 0.55 m
footprint contract.

Only new inflation intersecting the remaining route invalidates it. The active
target is discarded before installing a replacement. One attempt and a 0.25 s
planning budget are configured. Failure to find both goal and return paths
enters existing bounded LAND recovery; GUIDED, arm, takeoff and LAND retain
COMMAND_ACK followed by later same-session telemetry gating.

## Reproduction

After configuring the pinned ArduPilot/Gazebo environment and building the
Jazzy workspace:

```bash
./scripts/run_planner_flight_integration.sh \
  --output artifacts/v0.15.1-baseline-v0.15.0.json smoke --timeout 280

./scripts/run_sensor_replanning_integration.sh \
  --output artifacts/v0.15.1-sensor-replanning-graphical.json \
  smoke --graphical --timeout 280

./scripts/run_sensor_replanning_integration.sh \
  --output artifacts/v0.15.1-sensor-replanning-headless.json \
  smoke --timeout 280

./scripts/run_sensor_replanning_integration.sh \
  --output artifacts/v0.15.1-unreachable-after-discovery.json \
  negative-unreachable --timeout 280
```

## Accepted evidence

The unchanged v0.15.0 baseline passed. Both v0.15.1 positive runs discovered
cell `(9,10)`, invalidated the original straight room-one segment and completed
exactly one replan. The graphical and headless obstacle surface clearances were
0.345 m, above the configured 0.20 m margin; both reached the goal, returned,
crossed the doorway twice, landed and disarmed without prohibited contact.

The unreachable barrier produced one failed bounded attempt with the explicit
reason `no safe route after sensor discovery`. The armed vehicle stopped the
unsafe mission, entered LAND, reached `ON_GROUND` and disarmed without contact.
All three v0.15.1 runs stopped owned processes and ROS nodes and released UDP
9002/14550 and TCP 5760.

## Limitations

- The sensor observes one static obstacle in a known single-level world; there
  is no SLAM, probabilistic clearing or dynamic-object tracking.
- Planning is 2D cardinal-grid planning at one configured flight altitude, not
  generalized 3D planning or velocity control.
- Mapping associates the latest fresh pose by bounded receipt-time skew; it
  does not interpolate vehicle attitude through scan acquisition.
- The simulator lidar and independent Ground Truth evaluator are validation
  mechanisms, not real hardware or real-aircraft safety evidence.
- No multi-drone behavior, arbitrary MAVLink command, RC override, hardware
  support or v0.15.2 functionality is included.
