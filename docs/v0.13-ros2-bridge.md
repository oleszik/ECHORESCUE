# v0.13: ROS 2 Bridge and closed-loop simulator interface

## Scope and result

v0.13 runs one drone on one floor in a genuine closed loop:

```text
simulator Ground Truth -> typed observations -> ROS 2 -> mission knowledge
mission planner -> MoveGrid action -> ROS 2 -> atomic simulator movement
simulator actual state -> ROS 2 -> mission command confirmation
```

The mission explores from live observations, fuses occupancy and Survivor
evidence with the existing v0.12 components, and returns to base.  The direct
reference transport and ROS transport use the same `ClosedLoopMission` and
`ClosedLoopSimulatorBackend`; there is no scripted demo route.

This is a software-integration result, not evidence of real flight capability
or safety.  v0.12 benchmark profiles, benchmark artifacts and holdout seeds are
unchanged.

## Architecture and trust boundary

`src/echorescue/bridge_contracts.py` defines validated, immutable, ROS-free
domain messages and the grid/metric coordinate mapper.
`src/echorescue/closed_loop.py` contains the ROS-free mission and execution
state machines.  It remains importable in the normal Python installation.
`ros2_ws/src/echorescue_interfaces` contains generated ROS messages/action, and
`ros2_ws/src/echorescue_ros` performs conversion and transport only.

The simulator process is the sole owner of `GridWorld`, including obstacles and
Survivor Ground Truth.  The mission process receives neither the world nor a
shared environment reference: it plans solely from the probabilistic knowledge
map and separately fused Survivor evidence built from received observations.
Ground Truth is therefore available only on the backend side for sensing,
execution and evaluation.

Before each move, the backend's privileged Safety Shield checks the real cell.
It rejects an occupied destination with
`safety_shield_rejected_occupied_cell` and increments
`shield_interventions`.  Avoiding a simulated collision this way says nothing
about real sensor latency, dynamics, braking distance or flight safety.

The durable decision is [ADR 0014](adr/0014-ros2-closed-loop-boundary.md).

## Typed ROS contract

| Name | Type | Direction | QoS / behavior |
| --- | --- | --- | --- |
| `/echorescue/observations` | `echorescue_interfaces/msg/SensorObservation` | simulator to mission | reliable, volatile, keep-last 32 |
| `/echorescue/agent_state` | `echorescue_interfaces/msg/AgentState` | simulator to mission | reliable, volatile, keep-last 32 |
| `/echorescue/simulator/status` | `echorescue_interfaces/msg/BridgeStatus` | simulator to mission | reliable default, volatile, keep-last 10 |
| `/echorescue/mission/status` | `echorescue_interfaces/msg/BridgeStatus` | mission to simulator | reliable default, volatile, keep-last 10 |
| `/echorescue/move_grid` | `echorescue_interfaces/action/MoveGrid` | mission to simulator | action goal, feedback and terminal result |

Every observation contains session, agent, observation ID, sequence,
simulation timestamp, frame, observed cells with confidence, and separate
Survivor evidence.  Actual state contains its sequence, position, remaining
abstract energy, last completed command, motion state and error.  A movement
goal has a globally unique command ID, source and cardinal target, expected
state sequence, issue time and simulation-time validity.  The action reports
accepted/executing feedback and a completed, rejected, canceled or failed
terminal status.  `BridgeStatus` supplies sequence, heartbeat health and error.
No JSON string is used as a wire contract.

Reliable delivery reduces incidental loss in the local experiment but does not
replace application-level ordering and idempotency.  Volatile durability is
intentional: a new process/session must synchronize from a fresh backend
snapshot, not a DDS-retained sample from a former run.

## Coordinates and units

Discrete message coordinates use frame `echorescue/grid`, zero-based integer
cells, one floor, and cardinal steps.  The base is cell `(1, 1)`.  Simulation
time and validity are seconds; one successful cell move advances simulation
time by `1.0`.  Energy values are the simulator's abstract energy units.

`GridCoordinateMapper` defines a future metric boundary in ENU `map`: +x east,
+y north, +z up.  With origin `(ox, oy, oz)` at the south-west lower corner and
cell size `s` metres, grid `(x, y)` maps to its centre
`(ox + (x + 0.5)s, oy + (y + 0.5)s, oz)`.  Metric points map back using floor.
The default is a 1 m cell and origin `(0, 0, 0)`.  The discrete v0.13 action
does not pretend to command a continuous pose.

## Ordering, time and restart semantics

Observation timestamps drive probabilistic-map advancement and decay; state
and command timestamps use the same simulation clock.  Wall-clock scheduling
and DDS order are explicitly not reproducibility targets.  Watchdogs use
`time.monotonic_ns()`, so ROS/simulation clock pause does not hide a dead peer.

- Duplicate observation IDs and duplicate results are ignored.  Lower/equal
  sequences, old simulation timestamps and delayed state samples are ignored.
- A command remains pending until a `COMPLETED` result and a newer actual-state
  sample both name that command and report its target.  Timeout never implies
  success and blocks further commands.
- The backend caches each `(session_id, command_id)` result.  Resending a goal
  returns that result and never moves twice.  Source and expected state sequence
  are optimistic-concurrency preconditions.
- A backward simulation-time jump is treated as stale input.  A paused clock
  keeps command simulation validity fixed, but monotonic data and heartbeat
  watchdogs still expire.  A reset uses a new session ID.
- Foreign-session traffic is rejected.  A new mission may take over a retained
  simulator only after the previous monotonic heartbeat lease expires, then it
  synchronizes to a fresh observation/state pair.  Old-session commands remain
  rejected.

Mission states are `waiting_for_input`, `active_mission`,
`waiting_for_command_completion`, `communication_or_data_error`,
`controlled_stop`, and `mission_completed`.  Missing/stale observation, state,
result, heartbeat or action availability enters the error path and then a
controlled stop; no new movement is issued.  Recovery is explicit: restart
with a new session after a valid fresh state synchronization.  The backend also
stops independently when the mission heartbeat lease expires.

A discrete grid move is atomic.  Cancellation before the execution callback is
honored; after execution starts, that one cell step completes.  v0.13 does not
claim mid-cell braking or a continuous emergency stop.

## Supported environment and setup

The locally validated combination is Windows 11 host, WSL 2, Ubuntu 26.04
Resolute, Python 3.14.4 in the ROS environment, and ROS 2 Lyrical Luth
(`ros-lyrical-ros-base`).  Lyrical is the ROS 2 LTS release for Ubuntu 26.04.
Docker was not installed and was not required.  The normal Windows core remains
on Python 3.10.11 without ROS.

From Ubuntu 26.04/WSL, the reproducible setup script installs the official ROS
apt source, ROS base/dev tools, and creates a repository-local virtualenv:

```bash
cd /mnt/d/GitHub_Repos/ECHORESCUE
bash scripts/setup_ros2_lyrical.sh
source /opt/ros/lyrical/setup.bash
source .venv-ros2/bin/activate
repo_root="$(pwd)"
cd ros2_ws
"$repo_root/.venv-ros2/bin/python" -m colcon build --symlink-install
source install/setup.bash
cd ..
```

Using the virtualenv's absolute `python -m colcon` is required so installed ROS console
scripts run with the environment that contains `echorescue`.

## Demo, artifacts and failure runs

Start the two-process mission from the repository root after sourcing both ROS
and the overlay:

```bash
ros2 launch echorescue_ros closed_loop.launch.py \
  report_out:=replays/v0.13-ros2-report.json \
  replay_out:=replays/v0.13-ros2-replay.json
```

The default seed 7, 11x9 map and two Survivors are fixed in the launch file.
Logs show issued goals, feedback, results, timeouts and controlled stops.  The
report uses schema `echorescue-closed-loop-report/1.0`; the replay uses the
existing replay schema and exposes adapter state in each frame's `bridge`
field.  It can be viewed with the existing dashboard:

```bash
python -m echorescue.dashboard \
  --replay replays/v0.13-ros2-replay.json --host 127.0.0.1 --port 8000
```

The ROS-free reference run is:

```bash
python -m echorescue.closed_loop_demo \
  --report-out replays/v0.13-reference-report.json \
  --replay-out replays/v0.13-reference-replay.json
```

Examples for a dropped stream are:

```bash
ros2 launch echorescue_ros closed_loop.launch.py \
  drop_observations_after:=3 data_timeout_s:=0.5
ros2 launch echorescue_ros closed_loop.launch.py \
  drop_states_after:=3 data_timeout_s:=0.5
```

The complete automated process-level matrix, including forced process loss,
duplicates/delay and session restart, is `bash scripts/run_ros2_integration.sh`.

## Verification record

The separate-process ROS matrix completed locally on the environment above:

| Case | Observed result |
| --- | --- |
| normal mission | completed, 44 commands, 2/2 Survivors, returned to base |
| observation stream interrupted after sequence 3 | controlled stop, 3 commands |
| state stream interrupted after sequence 3 | controlled stop, 3 commands |
| duplicate and delayed samples | completed, duplicates/stale samples logged and ignored |
| mission process killed | backend's own heartbeat lease produced a controlled stop |
| simulator retained/restarted mission session | new session completed; old-session command rejected |

The harness also compares the direct and ROS reports by successful outcome,
Survivor count and the complete ordered movement-target sequence.  These match;
wall-clock timestamps and DDS delivery order are intentionally not compared.

Before v0.13 there are 304 pytest cases.  The older v0.11 figure of 291 tests
plus 37 subtests described pytest's 291 collected tests and separately reported
subtests.  v0.12's “275 total, then 13 targeted” came from `unittest discover`:
263 older unittest cases plus 12 new cases; the targeted set overlapped those 12
and added one case, so those runs must not be summed.  Pytest additionally
discovers 28 pytest-style multi-floor cases that unittest omits, yielding
291 + 13 = 304 before v0.13.  The canonical full command is therefore
`python -m pytest -q`; subtests are not added to the collected-test count.

The ordinary core suite, targeted bridge tests, ROS conversion tests, mypy,
compile checks and process matrix are rerunnable with:

```bash
# Normal host, no ROS dependency
python -m pytest -q
python -m mypy src
python -m compileall -q src tests

# Sourced ROS/overlay environment
.venv-ros2/bin/python -m pytest -q tests/test_ros2_conversions.py
bash scripts/run_ros2_integration.sh
```

The final normal run collected 322 cases: 321 passed, while the three-case ROS
conversion module was one expected module-level skip on the non-ROS Windows
host; 37 subtests also passed.  In the sourced ROS environment the conversion
module ran separately and all 3 cases passed.  Full mypy and compileall checks
also passed.

The open v0.12/v0.13 visual dashboard inspection could not be completed in this
session because the computer-use environment exposed no browser surface.  The
replay was generated and the dashboard server started successfully, but visual
layout remains explicitly unverified and must be checked locally in a browser.

## Known limits

- Exactly one simulated drone and one discrete floor; no new perception model,
  floor type or v0.12 study change.
- No vehicle dynamics, physics simulator, MAVLink, ArduPilot SITL, real flight
  controller, hardware-in-the-loop, hardware or safety certification.
- The ROS action transports one grid cell at a time; it is not a trajectory or
  velocity-control interface.
- The backend result cache is process-memory state.  Session IDs prevent a
  restarted process from replaying old work, but durable crash recovery is not
  provided.
- Reliable local DDS plus application guards were tested; multi-host discovery,
  hostile networks, security and real-time guarantees were not.
- Visual dashboard layout remains unverified for lack of an available browser.
