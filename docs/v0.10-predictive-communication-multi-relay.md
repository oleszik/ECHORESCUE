# v0.10 — Predictive Communication / Multi-Relay

## Research question and outcome

v0.10 asks whether an N-agent swarm can coordinate multiple Relay agents and
anticipate near-term communication loss without introducing new safety failures
or hiding Relay cost. The answer is qualified **yes** for the simulator's
bounded one-/two-Relay model.

Across holdout seeds 50–99, every profile completed 50/50 missions with
100% Survivor Recall, 100% return success, zero wall collisions, and zero drone
collisions. Moving from one to at most two reactive Relays improved mean
communication uptime by 0.050935 and reduced disconnected-agent steps by 11.38,
but added 27.36 active-Relay steps and 6.44 travel cells per mission. Prediction
improved mean uptime by another 0.023750 and reduced disconnected-agent steps by
0.50, queue mean by 1.450428, and TTL expirations by 1.94; it also added 15.68
active-Relay steps and 9.26 mission steps. Prediction is useful but not free or
universally better. The fair Relay-off control uses the identical v0.10
transport, priority, compaction, and routing stack with only Relay-role
assignment disabled; it also completed all 50 missions collision-free.

## Audit: what was already generic

The v0.9 core was already N-agent capable in the important lower layers:

- the communication snapshot contains Base plus all operational agents;
- range and wall-occluded LOS create an undirected link graph each step;
- deterministic BFS produces a stable shortest route;
- constrained transport fragments, queues, retries, expires, compacts, and
  reroutes messages over arbitrary multi-hop paths;
- map and Survivor synchronization, Final Sync, deconfliction, safety shielding,
  RTB, role assignment, task ownership, and failure recovery use agent
  collections.

The historical Relay policy was still two-agent-centered:

- configuration rejected every Relay strategy unless `drone_count == 2`;
- policy code selected fixed `drone-1`/`drone-2` participants;
- `relay_scout_id` represented a single partner and a single active Relay;
- direct Base–Relay–Scout checks and `route_hops=2` encoded one topology;
- one Scout could be placed in a holding state;
- metrics described one Relay/Scout pair and role switching only within it.

The reusable Network-aware work was retained: critical traffic precedes map
traffic, backpressure compacts only replaceable unsent map items, TTL and queue
cost remain visible, energy guards remain mandatory, and partial forwarding is
not treated as Final Sync.

## N-agent Multi-Relay model

`active_relays: set[str]` is the live collection. A `RelayDeployment` stores the
Relay ID, known-free target, all served agent IDs, upstream/downstream Relay IDs,
activation and minimum-release steps, reason, score, owned task ID, original
payload observation versions, and service counters. Runtime compatibility
fields remain for the old policies, but new behavior is driven by the
collection.

The bounded topology planner supports:

```text
Base ─ R1 ─ Scout
Base ─ R1 ─ R2 ─ Scout
Base ─ R1 ─ Scout A
          └─ Scout B
Base ─ R1 ─ R2 ─ Scout A
       └──────── Scout B       (when graph geometry permits)
```

All operational agents remain communication-graph nodes. Consequently a normal
agent may also form an opportunistic peer hop; explicit Relay roles describe
agents paying the placement/opportunity cost, not an artificial restriction on
which radios can forward. A Relay can serve multiple peers while range and LOS
links exist. Routes remain lexically deterministic shortest BFS paths. Transport
is limited to `max_active_relays + 1` hops for the v0.10 profiles.

## Assignment and targets

Candidate targets are known-free cells near the Base-to-primary-service corridor.
The list is sorted geometrically and capped at 48. One- and two-target chains
must preserve known LOS to Base, between Relay targets, and to the future/current
service position. Each candidate agent must have a known-free A* path, a
known-free return path, and energy for travel, return, reserve, and Relay margin.
No teleportation or world-map query is used.

The frozen lower-is-better candidate score is:

```text
8 × travel_steps
+ 12 × interrupted_task
+ role_penalty                    # RELAY 0, GENERALIST 4, specialist 8
+ floor(consumed_energy / 20)
- 50 × agents_helped
- min(queue_units, 144) / 4
- 15 × predicted_steps_prevented
```

Integer division is used for the queue term. Equal scores break by Relay count,
agent IDs, and target coordinates. Additional Relays therefore need to overcome
their own travel/role cost, while sharing one Relay across several agents is
rewarded.

## Activation, deactivation, and hysteresis

Reactive activation requires both:

1. an actual Base outage lasting at least three samples; and
2. critical/RTB state or at least 12 unsynchronized map/Survivor units.

Predictive activation substitutes a forecasted loss while the agent is still
connected. Relay agents never force Scouts to hold. Each agent may accept at
most two Relay deployments in a mission, deployments have an eight-step
cooldown, and the mission caps total activations at eight.

Release requires original payload versions to have reached Base, every served
agent to be connected, the six-step minimum hold to have elapsed, and three
consecutive stable samples. A 24-step maximum bounds opportunity cost. Release
completes/cancels the normal `RELAY_POSITIONING` task and restores the sticky
base role. These thresholds plus cooldown and the per-agent bound produced no
Relay Thrashing in development or holdout.

## Role, failure, dynamic-obstacle, and success integration

RELAY is a temporary generalized role. Activation creates ordinary
`RELAY_POSITIONING` ownership. If a Relay fails, that task is orphaned and a
deterministically scored, reachable, energy-safe agent receives the same task
ID. A four-agent seed-74 regression failed the active Relay at step 8: one Relay
task was reassigned, communication service resumed, all three operational agents
returned with full Recall, and collisions remained zero.

An observed dynamic obstacle on a Relay target follows the v0.8 invalidation
path. The Relay group is released, the blocked known cell is excluded, and a
new safe topology is selected deterministically. The controlled regression
asserts one path invalidation, one Relay replan, a different target, and no
teleportation.

Mission success still requires the existing Survivor-knowledge semantics,
collision-free flight, and operational landing. If landed agents retain
critical Survivor knowledge not present at Base, constrained transport enters
real Final Sync; a Relay payload flag alone cannot complete the mission.

## Predictive model

For the next `K=4` positions of the agent's current planned path, the forecast
computes known-map Base reachability, hop count, link margin (`range - Euclidean
link length`), and first expected disconnect step. It holds no hidden future
state: LOS uses only `KnowledgeMap`; unknown intervening cells break a predicted
link conservatively; future dynamic obstacles and world walls are never read.
The simulation supplies only the forecasting agent's current position, avoiding
live-position leakage from disconnected peers.

The predicted position becomes the service endpoint for the same Multi-Relay
topology search. Thus predictive and reactive profiles differ only in trigger
timing and the predicted-benefit score term. Routing, safety, energy, task, and
release semantics remain identical.

## Development and frozen parameters

Seeds 0–9 were used once for thresholds and then frozen before holdout.

| Parameter | Frozen value |
| --- | ---: |
| Activation outage | 3 steps |
| Minimum unsynchronized payload | 12 units |
| Minimum Relay hold | 6 steps |
| Deactivation stability | 3 steps |
| Maximum Relay duration | 24 steps |
| Maximum active Relays | 1 for control B; 2 for C/D/E |
| Maximum deployments | 8 mission-wide; 2 per agent |
| Candidate limit | 48 |
| Prediction horizon | 4 steps |

Development means (10 seeds) were: uptime 0.434084 / 0.533438 / 0.554630 /
0.574581 and disconnected steps 258.5 / 269.3 / 230.7 / 265.2 for Off /
Reactive-1 / Reactive-2 / Predictive-2. All 40 missions succeeded and were
collision-free. Prediction helped absolute disconnected time on four seeds and
activated unnecessarily on seeds 0 and 8, which motivated reporting both
benefit and cost without further tuning.

## Holdout design

The holdout is seeds 50–99, four agents, communication range 8,
constrained/local knowledge, generalized roles, Visual perception, Noise/Smoke
off, dynamic obstacles off, and failure injection off. A/B/C/D/E map to:

- A: Relay roles off, with the same v0.10 transport/backpressure stack;
- B: reactive new architecture, maximum one Relay;
- C: reactive new architecture, maximum two Relays;
- D: the same reactive Multi-Relay baseline as C (reused, not rerun);
- E: predictive new architecture, maximum two Relays.

## Paired effects and per-seed analysis

Mean paired changes (`second - first`) are:

| Comparison | Uptime | Disconnected | Duration | Queue mean | TTL | Active Relay | Travel |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| B one Relay − A off | +.106589 | −8.22 | +24.12 | −1.962 | +9.00 | +41.76 | +8.78 |
| C two Relays − B one | +.050935 | −11.38 | +8.32 | −1.166 | −5.42 | +27.36 | +6.44 |
| E predictive − C reactive | +.023750 | −0.50 | +9.26 | −1.450 | −1.94 | +15.68 | −1.18 |

Twenty-seven of 50 reactive-two missions actually used two simultaneous Relays;
14 predictive missions did. Prediction recorded 2,738 prevented-disconnection
agent-steps, with five unnecessary activations across seeds 52, 53, 58, 68, and
92. It reduced absolute disconnected steps on 29/50 seeds.

Notable seeds:

- 62 had the largest two-vs-one uptime gain (+0.473844) but also the largest
  added active time (+144); Prediction was worse than reactive there.
- 74 is the strongest demo: predictive-vs-reactive uptime +0.327725,
  disconnected steps −129, two simultaneous Relays, 113 prevented steps, full
  Recall/return, and zero collisions.
- 95 combined 119 prevented steps with uptime +0.068788 and disconnected steps
  −24, at 72 extra active steps over reactive.
- 65 showed the largest reactive-to-predictive TTL improvement (−41 in its raw
  profile rows) and 71 prevented steps.
- 22 seeds had worse uptime with two rather than one Relay; this is the central
  marginal-gain warning, not hidden by aggregate improvement.
- Seed 57 had the highest predictive opportunity-cost increase (+121 active
  steps versus reactive); seed 62 had a negative prediction effect despite a
  successful mission.
- No Relay profile showed the defined >2 deployment cycles per agent Thrashing,
  no Relay profile timed out Final Sync, and no Relay profile regressed mission
  success.

## Replay and dashboard

Replay schema 2.4 adds per-frame active Relay IDs, deployment topology, targets,
served agents, upstream/downstream Relay IDs, activation reason, forecast
disconnect step, and operator-safe forecast values. Existing role badges and
per-agent cards naturally render multiple Relays; link rendering continues to
use the graph. Event styling covers activation, topology change, prediction,
and deactivation. Older strategies retain schemas 1.5–2.3 and byte-identical
off behavior.

The committed demo is
[`replays/seed_74_predictive_multi_relay.json`](../replays/seed_74_predictive_multi_relay.json).
It forecasts its first loss at step 5 for step 9, activates a Relay without
teleportation, later displays two simultaneous Relays and a three-hop planned
topology, transfers all three Survivor confirmations to Base, releases every
Relay, completes in 159 steps, returns all four agents, and has zero collisions.

Run it with:

```bash
python -m echorescue.dashboard \
  --replay replays/seed_74_predictive_multi_relay.json \
  --benchmark benchmarks/predictive_multi_relay_50_seeds.json
```

## Limitations and next question

- The optimizer is deliberately bounded to at most two explicit Relays and 48
  known-free candidate cells; it is not a mesh-network solver.
- Forecasting is geometric and deterministic, not an RF fading model.
- Other moving peers are excluded from prediction, which is conservative but
  can miss future opportunistic paths.
- Role assignment is centralized simulation logic; constrained/local mode still
  has no distributed role-consensus protocol.
- Prediction improves aggregate uptime modestly but raises duration and active
  time, and five holdout activations were unnecessary.
- The fair Relay-off control isolates role assignment, but it is not the legacy
  `off` transport profile; conclusions therefore apply to the shared v0.10
  constrained-transport stack.

The next separate research stage is v0.11 Multi-floor / 2.5D. It is not part of
this change.
